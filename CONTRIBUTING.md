# Работа над AI Home Modeler

## Перед началом

1. Прочитайте `knowledge.md` и документы, связанные с задачей.
2. Создайте рабочую ветку от актуальной целевой ветки.
3. Для изменения требования укажите связанный сценарий и критерии приёмки.
4. Для существенного технического решения создайте ADR или обновите предложенный.

## Локальный запуск

Требуются Node.js 24, Python 3.12–3.13, `uv`, Docker и Docker Compose.

```bash
cp .env.example .env
make bootstrap
make infra
make api
make web
```

Web-прототип доступен на `http://localhost:3000`, OpenAPI — на
`http://localhost:8000/api/docs`, MinIO Console — на `http://localhost:19001`.

## Проверки

Перед передачей изменений на ревью выполните:

```bash
make check
npm run build --workspace @ai-home-modeler/web
docker compose config --quiet
```

После изменений кода или документации обновите граф по
[`docs/knowledge-graph.md`](docs/knowledge-graph.md) и проверьте новые узлы и
связи с существующими областями проекта.

Минимальный набор для pull request:

- задача связана с P0-сценарием либо содержит объяснение ценности;
- добавлены содержательные тесты для доменных правил и контрактов;
- границы модулей не нарушены;
- персональные данные, планы и prompts не попадают в логи;
- изменения схемы имеют новую версию или совместимую миграцию;
- документация и `knowledge.md` отражают итоговое состояние;
- граф обновлён; новые сущности и подтверждённые связи отражены в нём либо в PR
  объяснено, почему изменение не повлияло на граф;
- локальные проверки и CI прошли.

## Правила кода

- Web использует строгий TypeScript и компоненты с доступной семантикой.
- API использует Python type hints и versioned routes под `/api/v1`.
- Денежные значения хранятся в minor units вместе с ISO 4217 currency code.
- Координаты и размеры канонической модели хранятся в метрах.
- Создающие команды и фоновые задания проектируются идемпотентными.
- Модуль владеет своими таблицами. Межмодульная связь идёт через application
  services или события, а не через импорт чужих репозиториев.

## Git и ревью

Коммиты должны описывать один связный результат. Не смешивайте форматирование,
рефакторинг и изменение поведения без необходимости. Pull request создаётся после
локального ревью этапа; публикация считается завершённой только после проверки
удалённого commit SHA.
