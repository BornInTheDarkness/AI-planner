# ADR-004: идемпотентные фоновые задания

- **Статус:** Proposed
- **Дата предложения:** 2026-09-17
- **Владелец:** требуется назначить

## Контекст

Импорт, генерация, рендер и экспорт дольше HTTP timeout и зависят от нестабильных
провайдеров. Повтор запроса не должен удваивать результат или стоимость.

## Решение

API сохраняет job и outbox атомарно, затем возвращает `202`. Worker получает lease,
пишет heartbeat и завершает job транзакционно. Создающие команды используют
idempotency key. Состояния: `queued`, `running`, `succeeded`, `failed`, `cancelled`.
После ограниченных retries с backoff сообщение уходит в DLQ.

## Последствия

Появляется eventual consistency и необходимость явного UX прогресса/повтора.
Результат публикуется только после полной валидации. Redis допустим для MVP, но БД
остаётся источником истины о состоянии job.

## Пересмотр

При требованиях managed queue, multi-region delivery или потоке, который нельзя
надёжно реализовать на Redis.
